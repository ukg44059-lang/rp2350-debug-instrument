# 单板下载调试器 + 逻辑分析仪架构提案

日期：2026-11-02（America/Denver）。用户已确认：同一块 Waveshare RP2350B-Plus-W，同时运行下载调试与逻辑分析功能。本文为开发规划，尚未实现逻辑采样固件，不改变已验证的下载器。

实施更新：随后用户授权开发，0.2.0 已交付基础采集工程及独立 USB 接口，实机结果与未完成项见 [开发记录](logic-analyzer-bringup-2026-11-02.md)。下文保留原规划，不能将全部阶段视为已实现。

## 1. 产品目标与边界

一个固件、一个 USB 连接，提供两个可独立使用和联合操作的功能：

- 下载调试：延续 CMSIS-DAP v2 → OpenOCD → GDB，当前已验证 STM32F407 的 SWD 下载与基本源码调试。
- 逻辑分析：输入引脚 → PIO → DMA → SRAM → USB → PC 波形/协议分析。
- 联合工作：先装载程序，武装采集，再启动目标；也能在目标运行和调试访问期间捕获 GPIO / 串行总线。

下载器“通用”依靠芯片支持矩阵逐步扩展。当前不表示所有 MCU 都能下载；JTAG 尚待实现。新增逻辑功能不得占用未来 JTAG 已预留引脚，也不得回退当前 SWD 功能。

## 2. 单芯片资源分配

RP2350 官方提供双核最高 150 MHz、520 KB SRAM、3 组 PIO / 12 个状态机、16 路 DMA 以及 USB 1.1。该板具有 16 MB 板载 Flash 和 PSRAM 预留接口；不能假定已安装 PSRAM。Flash 容量不能等同于实时采样 RAM。

| 资源 | 初版分配 | 约束 |
| --- | --- | --- |
| Core 0 | 唯一 TinyUSB 所有者、CMSIS-DAP、USB 控制与采样数据上传 | 两核不得并发调用 TinyUSB；DAP 处理保持有界 |
| Core 1 | 采集状态机、参数装载、PIO/DMA 管理、触发与结果封装 | 不逐点软件采样；通过有界消息队列与 Core 0 交互 |
| PIO0 | 保留给后续 SWD/JTAG 加速 | 当前 GPIO SWD 实现继续使用 |
| PIO1 | 逻辑采样与触发 | 初版 1 个采样 SM；复杂触发按需要分配其他 SM |
| PIO2 | 预留 | 不默认被无线功能占用 |
| DMA | 预留 2–3 路用于采样搬运、环形/链式控制 | 确切通道数随触发方案冻结，避免和未来调试 DMA 冲突 |
| SRAM | 首版目标采样缓冲 256 KiB | 其他空间供 USB、DAP、栈与控制；以链接 map 和栈水位核实 |
| Wi-Fi / PSRAM | 初版不启用 | 后续扩展需独立验证资源、实时性和电气连接 |

双核隔离管理职责，采样时序由 PIO 决定，不能因双核分工就忽略 DMA/总线争用。DMA 缓冲布局与 SRAM bank 分布需结合实测优化；不先承诺任意并发负载下的最高采样率。

## 3. 引脚与输入接口

| 功能 | 引脚规划 |
| --- | --- |
| SWCLK/TCK | GP2，保持现有接线 |
| SWDIO/TMS | GP3，保持现有接线 |
| nRESET | GP4，预留，当前用户未接 |
| JTAG TDI / TDO / nTRST | GP5 / GP6 / GP7，继续预留 |
| 逻辑 CH0–CH7 | GP8–GP15，连续 8 位，便于 PIO 采样打包 |
| 公共参考 | GND；下载器、分析仪和目标共地 |

本板配置与引脚图支持上述 GP8–GP15 分配；外接测试前再次按板上丝印确认。GP23 是板载 LED，GP36–GP39 与无线模块有关，不用于首版采集。16 通道属于后续扩展，需要重新核对连续引脚可用性和采样格式，暂不冻结第二组引脚。

所有分析通道保持输入，不驱动被测总线。第一版仅用于已确认的 3.3-V 数字信号；5-V、1.8-V、RS232、RS485、CAN 等必须通过合适的前端/收发器处理，不能直接接裸 GPIO。增加专用输入缓冲、限流及保护前端时，要评估输入阈值、带宽、传播偏差和总线负载。

分析仪需要另接观察线：现有 SWD 三线只负责调试，不会自动读出任意目标引脚。首次可将 STM32 PB2 接 GP8，保留原 SWD 接线，用低采样率捕获已知的 200-ms 翻转。也可外部分支观察 SWCLK/SWDIO，但必须计入额外负载和线长。

## 4. 首版能力与采样深度

建议先实现 8 通道、3.3-V 输入、有限长度采集，基础采样率目标 100 kS/s / 1 MS/s / 10 MS/s；后续再实测评估 25/50 MS/s。所有数字为开发目标，不是已验收性能。软件报告实际分频器对应的采样率，不仅回显用户请求值。

PIO 每点读 8 位，以四点打包成 32 位 FIFO 数据，DMA 搬运到 SRAM，使每个 8 通道样点只占 1 字节。若实现中每点保存为 32 位而未打包，下面深度将缩小为四分之一，必须在格式与实际分配中核对。

以 256 KiB 采样缓冲、不压缩、8 通道为例：

| 采样率 | 样点数 | 连续记录时长 |
| --- | ---: | ---: |
| 100 kS/s | 262144 | 约 2.621 秒 |
| 1 MS/s | 262144 | 约 262.144 ms |
| 10 MS/s | 262144 | 约 26.214 ms |
| 50 MS/s（后续目标） | 262144 | 约 5.243 ms |

16 通道按每点 2 字节存储时，相同缓冲的深度和时长减半。采样率不是能可靠解码的总线时钟：优先按最快相关信号的约 5–10 倍配置，用实测边沿与解码结果确认。例如初版 10 MS/s 适合先验证 UART、常用 I²C 和约 1-MHz SPI，不宣称覆盖所有高速 SPI。

USB 为 Full Speed，标称线速上限 12 Mbit/s，实际应用吞吐还要扣除协议及共享开销。8 通道 10 MS/s 原始数据已达 10 MB/s，无法靠该 USB 接口无损持续上传。因此第一版采用“设备高速采到 RAM，停止后上传”；采样和 USB 调试可同时运行，但高速采样数据不要求实时送达 PC。低速连续流作为独立后续模式，必须显式报告溢出/丢样。

## 5. 采集与触发流程

状态机：`IDLE → ARMED → CAPTURING → COMPLETE → UPLOADING → IDLE`，并具有取消、超时和错误状态。配置在武装时冻结；同一缓冲任何时刻只能有一个写入方，结果上传完成前不得被新采集覆盖。

按以下顺序增加触发能力：

1. 立即触发，定长采集；先验证采样率、数据打包和完整性。
2. 指定通道上升沿/下降沿触发，先只采触发后数据；触发判定由 PIO/硬件流程实现。
3. 环形预采样 + 触发后定长采集，提供可配置前/后比例，如 25% / 75%。
4. 多通道模式、脉宽和协议条件触发。

触发位置必须定义为样点索引，记录 `trigger_index` 与有效样点数。PIO 检测延迟、DMA 在途数据和环形指针快照都有可能产生偏移；不能用“CPU 看到事件的时间”冒充精确触发位置。用已知波形验证触发边界后，才发布其精度。UART/I²C/SPI 解码先放 PC，不抢采样实时路径。

长时间观察稀疏信号可后续评估游程压缩，但需要保留每段持续样点数和完整性标记；不能把压缩率当成对任意高速数据都适用的容量保证。

## 6. USB、主机与 AI 接口

USB 采用复合设备，在保留现有 CMSIS-DAP 接口的基础上增加独立逻辑分析 Vendor Bulk 接口。CDC 维护接口按资源保留。分析仪使用独立 WinUSB 接口 GUID；不能让现有 `probe_cli` 把新增接口误识别为 CMSIS-DAP。新固件需要更新描述符、绑定信息和版本号，并测试 Windows 更新枚举。

Core 0 统一调度所有 USB 工作：DAP/调试控制优先，采样数据分块上传，在每块之间处理控制请求。两个功能共享同一 USB 总带宽。不能让 `upload` 长循环独占 USB，也不能让 Core 1 直接调用 USB API。

PC 侧继续使用 C++17，先增加独立分析仪 CLI / 库，后续与调试服务整合。按接口 GUID + 设备序列号绑定同一块板，OpenOCD 和分析客户端分别拥有各自接口，不能互相 reset 整个 USB 设备。

建议提供：`info`、`configure`、`arm`、`status`、`cancel`、`fetch`。采样数据传输包含版本、会话 ID、通道掩码、实际采样率、样点数、触发位置、块序号、偏移、长度、完整性校验及溢出标记；原始二进制是主数据，CSV/VCD 是导出格式。设备正常工作时不通过文本/JSON 搬运每个样点。

第一版不自研大型波形 GUI：先实现可靠采集与数据导出，再评估现有波形查看器和解码器接口。自定义协议不会自动兼容 PulseView，若采用现成上位机必须实现匹配驱动/格式并验收。

AI 组合流程：`configure → arm → 下载/复位/继续目标 → 等待完成 → fetch → 协议解码/时序统计 → 附原始数据的分析结果`。精确关联软件事件时优先由目标输出 GPIO 标记并同步采样，主机命令时间不具备样点级同步精度。GDB 暂停可能改变目标外设波形，分析报告必须记录当时的调试操作。

## 7. 分阶段交付与验收

| 阶段 | 交付 | 通过条件 |
| --- | --- | --- |
| LA0 | 保留下载器版本、冻结引脚与数据格式 | 现有烧录/源码调试流程继续可复现 |
| LA1 | 8 通道 PIO + DMA 定长采集，独立 USB 接口，C++ 主机导出 | 已知波形样点、顺序、长度、校验全部一致；报告实际采样率 |
| LA2 | 边沿触发，再扩展环形预触发 | 验证触发边界、前后样点数、超时、取消和无信号场景 |
| LA3 | 单板并发 | 采集中完成 F407 下载/校验/GDB 操作；采样完整且调试可响应 |
| LA4 | PC UART/I²C/SPI 解码、AI 联合流程 | 与 F407 发送的已知内容及故障注入比对，不丢报溢出 |
| LA5 | 性能/容量扩展 | 更高速率、更多通道、低速连续流、压缩/PSRAM 逐项实测 |

并发测试至少包含三类：单独采样、采样 + 调试访问、数据上传 + 调试访问。分别记录样点完整性、PIO FIFO/DMA 溢出、DAP 延迟、采集时间和上传耗时。检测到 FIFO 停顿或溢出时，必须标记本次波形无效/有缺口，不能默默按等间隔样点继续解码。

第一块 F407 提供可重复的测试源：PB2 闪烁验证长时序，定时器输出验证频率，UART 已知字节序列和 SPI/I²C 已知事务验证解码。高采样率与边沿位置的绝对精度，后续使用独立仪器交叉验证。

## 8. 代码组织建议

```text
firmware/
  app/              USB 调度与双核消息
  debug_probe/      现有 DAP/传输逻辑，按需要渐进迁移
  logic_analyzer/   配置、状态机、触发、缓冲所有权
  pio/              采样/触发程序；调试传输单独分配
host/
  logic/            WinUSB 分析接口、采集文件、CLI
docs/
  logic-analyzer-architecture.md
artifacts/
  captures/         原始波形、元数据、导出及验收日志
```

本阶段只建立设计文档，不先重构已工作的目录。实施时先加最小模块，再根据实际边界调整。继续使用 C++17 + Pico SDK，底层 C 库保留，PIO 汇编负责采样；所有文件保持在 G 盘项目内。
