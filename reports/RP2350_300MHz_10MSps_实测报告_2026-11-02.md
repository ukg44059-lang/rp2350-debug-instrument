# RP2350 300 MHz / 10 MS/s 实测报告

日期：2026-11-02。项目全部文件位于 `G:\material\week_prj\ai_debuginstructment`。

## 结果与验收范围

RP2350 已刷入 C++17 一体化固件 **0.2.2 / 300 MHz**，八路 **10 MS/s** 定长采集、USB上传和CRC检查已跑通。**整体尚未稳定验收**：最终18轮中，11轮通过严格波形检查，7轮失败；密集SWD读取还会出现No ACK。不得仅凭flags=0或CRC通过认定输入波形正确。

用户已目视确认RT1064 B9 LED闪烁。本轮没有擦写RT1064 Flash；测试仅临时修改信号速率和八个输出pad配置，结束时恢复1000 step/s与原pad值0x10B0，B9和八路信号程序继续运行。

## 固件修改

- 系统主频从150 MHz提高为300 MHz，两个核心共享clk_sys。先将内部核心稳压器设定1.20 V并等待10 ms，然后切换PLL。
- RP2350使用ROM初始化XIP；仅修改板头文件中的boot2分频宏不足以保证运行时Flash频率。新增禁止内联的SRAM函数，在core1/DMA启动前把QMI窗口0分频提高至至少4，保留ROM读格式，300 MHz下Flash SCK不超过75 MHz。链接映射确认该函数位于0x20000110。
- USB PLL与USB时钟保持48 MHz；系统微秒计时基于晶振参考，不按CPU周期硬编码延时。SWD的CMSIS-DAP CPU_CLOCK同步为300000000，避免沿用150 MHz换算。
- 启动时通过SDK FC0测量clk_sys，使用板载晶振参考，检查在目标频率±1 MHz内；检查失败则进入BOOTSEL。采集JSON实际报告system_clock_hz=300000000。没有外部频率计校准或长期温升测试。
- 构建支持150/300两个独立目录，默认300 MHz；协议仍为1，未提高原有10 MS/s请求上限。

300 MHz属于超频，超出官方标称150 MHz工作频率；1.20 V是本次设定值，不是厂商对300 MHz的保证。参见[Raspberry Pi RP2350官方资料](https://datasheets.raspberrypi.com/rp2350/rp2350-datasheet.pdf)以及工程内Pico SDK 2.2.0的hardware_clocks、hardware_vreg与QMI寄存器定义。

## 采样速度与容量

PIO每点执行IN与JMP两条指令。300 MHz下使用整数分频15：

`300000000 / 15 / 2 = 10000000 samples/s`

| 项目 | 实际配置/结果 |
|---|---|
| 通道 | GP8–GP15，共8路 |
| 每点 | 8位，1字节 |
| 采样间隔 | 100 ns |
| 最大样点 | 262144 |
| 一次记录时长 | 26.2144 ms |
| 最终18轮满缓冲USB上传 | 398.028–425.292 ms，平均406.157 ms |
| 采集模式 | SRAM定长采集后上传，不能连续以10 MB/s向电脑传流 |

150 MHz旧固件本来就支持10 MS/s，使用分频7.5；300 MHz使该档可以整数分频，但采样请求仍必须显式设为10000000。CPU超频不会自动改变电脑端原来请求的100 kS/s。10 MS/s也不等于10 MHz输入带宽；本次已知输入最高25 kHz。

## 测试过程与证据

最终原生C++工具回归共18轮：1轮1 MS/s、16轮10 MS/s（8通道各上升/下降沿）、1轮10 MS/s立即采集。信号源RT1064每秒递增50000次，CH0=25 kHz，其余逐路二分。总计4718592样点，所有样点长度、分块CRC及传输检查通过，所有采集flags=0。

严格检查器同时检查触发首电平、逐通道频率/半周期和八位计数序列。此前已有规则只允许一个样点混合旧/新进位电平，并不删除原始样点；本次未放宽该规则。最终11轮通过，7轮失败：

| 触发 | 通道 | 失败原因 |
|---|---|---|
| 上升沿 | CH2 | sample 227992计数跳变/毛刺 |
| 上升沿 | CH3 | sample 94396计数跳变/毛刺 |
| 下降沿 | CH4 | sample 89594计数跳变/毛刺 |
| 下降沿 | CH5 | sample 204792计数跳变/毛刺 |
| 上升沿 | CH6 | sample 25596计数跳变/毛刺 |
| 上升沿 | CH7 | 触发首样点电平不符 |
| 下降沿 | CH7 | sample 217589计数跳变/毛刺 |

早期失败数据中出现过0x1F→0xE0→0x20的单样点异常，超出正确计数进位涉及的变化位，不能算作正常异步进位混合。毛刺来源尚未区分为输出波形、接线/串扰、输入采样或超频时序问题。临时把RT1064输出pad从0x10B0改为0x1010仍出现失败，因此该修改已撤回。

证据位于 `artifacts/overclock-300/`：

- `native-test-summary.json`、`native-final-test.log`：最终18轮结果，失败测试返回非零。
- `native-*.bin/json/vcd/edges.csv`及对应capture/check日志：最终原始数据与检查结果。首次毛刺样点另保留在`native-first-glitch.bin`。
- `first-10M.*`：首次300 MHz / 10 MS/s完整通过的八路数据。
- `final-default-source-10M.*`：一键采集脚本验证，信号源已恢复默认低速；该短窗口不足以验证最慢几路的完整周期。
- `weaker-drive-experiment/`：临时弱驱动试验记录；并非最终接线配置。
- `final-selftest.log`：100000个DAP边界/模糊输入测试、协议边界/CRC标准向量、100次USB序列号查询及USB逻辑接口自检通过。

## SWD并发与遗留问题

300 MHz下，以10 kS/s采集65536点、同时执行3轮SWD读取（CPUID、demo_signature、signal_count），目标保持运行，计数递增，完整波形检查通过。证据为`concurrent-10k.*`、`concurrent-10k-swd.json`。这是较低采样率、有限负载并发验证，不代表10 MS/s加持续密集SWD读已通过。

更强压力测试出现过No ACK。在150 MHz对照下、即使不执行逻辑采集，持续切换CPUID/签名/计数地址读取也能复现失败。因此SWD问题不能仅归因于300 MHz；根因尚未确认。失败日志包括`test-150-comparison.log`、`test-1MHz-swd-failed.log`、`test-500kHz-swd-failed.log`、`test-100kHz-swd-failed.log`及`test-shared-usb-cpuid-failed.log`。原有读写/调试功能保留，但密集并发稳定性仍未解决。

Windows端另发现pyOCD的libusb连接会占用复合USB设备句柄，使另一个原生C++逻辑工具打开时返回Windows=5。诊断脚本已改用同进程共享USB对象，也仍能复现SWD压力问题；没有把它当作跨进程访问问题已解决。

后续应优先把毛刺与SWD应答失败分开定位：对照150/300 MHz的相同输入，使用单通道已知波形隔离多线同时翻转，再核实实际SWD波形、公共地回路和接线串扰。未解决前，不应依靠异常触发或毛刺样点作精确协议判断。
